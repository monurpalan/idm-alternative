# Memory: Shardload, IDM, Gopeed, AB Download Manager, FDM (2026-11-01)

Windows 11, the development machine. Shardload is current `main` (0.1.2), a release build made
with another identifier so it could run next to the installed copy (`TAURI_CONFIG` with
`"identifier": "io.github.monurpalan.shardload.memtest"`, `--features tauri/custom-protocol`),
in a profile of its own (`SHARDLOAD_HOME`). Script: [bench/memory/measure.py](../memory/measure.py),
tables by [bench/memory/summarize.py](../memory/summarize.py).

## What is measured

The sum over a client's whole process tree, the app and everything it started (Shardload's
WebView2, AB DM's JVM launcher and JVM, IDM's helpers), of:

- **Private bytes (commit):** memory the processes asked for that only they use, in RAM or in
  the page file. The most stable number, and what grows when a program needs more.
- **Working set:** what is in RAM now, shared pages (DLLs, the WebView2 runtime shared with Edge)
  counted in every process.
- **Private working set:** the part of the working set that is the process's own: what closing
  it would give back to the rest of the system.

States: cold start to a visible window (Shardload: also to its page loaded); 60 s idle with the
window open; 60 s minimized; a 1 GiB download from the local test server, unlimited and with the
server holding it to 10 MiB/s (peak and average, sampled four times a second); 60 s with the
window closed to the tray. A state's value is the median of one sample a second over its last
10 s; tables give the median of 3 runs. MB = 10^6 bytes.

### Where Shardload's memory goes

One snapshot, idle with the window open (unfocused), private / working set / private WS in MB:

| Process | Private | Working set | Private WS |
|---|---|---|---|
| shardload.exe (the app: engine, list, tray) | 13.1 | 42.8 | 10.5 |
| WebView2 browser | 41.4 | 7.1 | 3.5 |
| WebView2 GPU process | 92.9 | 1.2 | 0.6 |
| WebView2 renderer (the page) | 42.5 | 17.2 | 11.4 |
| WebView2 utility | 7.8 | 0.0 | 0.0 |
| WebView2 crashpad handler | 4.6 | 25.6 | 2.5 |

About 93 % of the commit is WebView2, and almost half of that is the GPU process, which stays
on purpose: drawing without it changes the window's colours (it loses the monitor's colour
profile). The app itself, downloads included, is 13 MB idle.

## Caveats

- **Focus changes WebView2's working set by 5×, its commit not at all.** Started from a script
  while someone works at the machine, the window does not get the focus; Chromium then trims it
  to ~77 MB working set / ~17 MB private WS. In 2 samples where the new window did get the focus
  it held ~430 MB working set / ~133 MB private WS. Kept on top without the focus it was still
  trimmed. Commit stayed at ~200 MB either way. The focused case was not forced (taking the
  focus from the person at the machine), so its numbers are 2 samples, not medians of 3.
- **Minimized was higher than unfocused** (118 vs 77 MB working set): minimizing sets the
  WebView2 memory target to Low, but the window had been unfocused and trimmed already.
- **Downloads ran with the window open**, after it was restored from minimized; the restore
  brings part of the page back, so the download states start from ~200 MB working set.
- **Shardload's unlimited download is a loopback download** (1 GiB in 1.3–2.1 s); its peak shows
  the engine's buffers at full speed, not what a real connection needs.
- **Gopeed is its web-server build (engine only).** Its desktop app adds a Flutter UI; the
  portable build was downloaded but not run here (running a just-downloaded program needs the
  user's OK). Its download also used Gopeed's default connections and was slower on loopback
  (6–16 s).
- **FDM** has no command line or local API to start a download, so it has no download state.
- **The tray state comes after the downloads.** For AB DM the JVM keeps the heap the downloads
  grew (593 MB commit in the tray against 443 MB idle before); for FDM, closing the window
  keeps the Qt UI's memory (210 MB, as with the window open).
- The test server held the 10 MiB/s case per address; each download uses a new address (an
  address asked for again starts with the budget it saved meanwhile, which first spoiled a run).

## Shardload against the others

- **IDM** is in a class of its own: a native Win32 window, ~11 MB commit open, 15–20 MB while
  downloading, ~14 MB in the tray.
- **Shardload in the tray** (window closed) is close to IDM: 1 process, 18 MB commit, 15 MB
  private working set. It drops the whole WebView2 when the window closes.
- **Shardload with its window open** commits about 200 MB, as much as FDM's Qt UI and less than
  half of AB DM's JVM (443 MB); in RAM 17 MB unfocused to ~133 MB focused, against FDM's
  ~158 MB and AB DM's ~269 MB. The engine's own share is 13 MB; the rest is WebView2.
- **Downloading:** Shardload 240–275 MB commit; AB DM 530–670 MB; IDM 15–20 MB.
- **In the tray** Shardload gives the window's memory back; FDM and AB DM keep theirs (IDM is small
  either way).
